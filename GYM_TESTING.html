01

Launch the stack

Three data services back this API before it will boot. Get each one live first, then bring the server up.

  1. Redis Cloud — used for caching. Confirm the instance is reachable and the connection string is in .env.
  2. Supabase (PostgreSQL) — holds the members table plus auth. Run migrations against it before seeding.
  3. MongoDB Atlas — holds the workouts collection. No schema migration needed, just a reachable connection string.
  4. Copy .env.example to .env and fill in all three connection strings, then seed and start the server.
npm run migrate npm run seed npm run dev
02

Where the data lives

Three stores, three jobs. Nothing about a member's identity lives next to their workout history — the API is the only thing that joins them.

PG

Supabase

PostgreSQL + Auth

System of record for the members table and for authentication — registration, login sessions, and the admin account.

  • id, full_name, email, phone
  • subscription_plan, subscription_status
  • allowed_workout_days
MG

MongoDB Atlas

Workouts collection

Every workout a member starts, stops, and leaves feedback on. Read back for history, the dashboard chart, and admin reports.

  • memberId, workoutType
  • startTimestamp, endTimestamp, duration
  • calories, feedback
RD

Redis Cloud

Caching layer

Sits in front of the heavier reads — dashboards, statistics, member lists — so repeat requests don't refetch from Postgres or Mongo.

  • No test cases below hit it directly
  • Invalidate on write, verify on repeat GET

04

Configure Postman

Sessions are cookie-based, same as the login flow itself.

  1. Use Postman desktop with cookie handling enabled — logging in as either a member or the admin sets an HTTP-only session cookie automatically.
  2. Member and admin sessions don't mix. Log out (or use a second cookie jar) before switching roles.
  3. After starting a workout, copy its returned id to stop it or attach feedback — both routes take the workout id in the URL path.
{"email": "hassan.brown010@pulsegym.com", "password": "password12345"}
MEMBER

What a member can do

Everything below runs under a member's own session. Check items off as you verify them — throwaway registrations only for the delete-adjacent flows.

Authentication

POST
localhost:3000/api/auth/register

Body: fullName, email, password. Password needs 6–255 characters. Expect 201.

POST
localhost:3000/api/auth/login

Body: email, password. Sets the session cookie. Expect 200 with the member object.

POST
localhost:3000/api/auth/refresh

No body. Refreshes the session token. Fails with 401 once logged out.

POST
localhost:3000/api/auth/logout

No body. Run last in any test pass. Expect 200.

Profile & subscription

GET
localhost:3000/api/members/me

The logged-in member's own record — plan, status, allowed workout days.

GET
localhost:3000/api/members/me/subscription

Just the plan + status pair, for a lighter read than the full profile.

GET
localhost:3000/api/members/me/workout-days

Which days this member's plan allows them to train. Requires a session — 401 without one.

Workouts

POST
localhost:3000/api/workouts/start

Body: {"workoutType": "yoga"}. Type must be one of the seven allowed values. Save the returned id.

POST
localhost:3000/api/workouts/{id}/stop

Body: {"calories": 250}. Closes out the workout with an end timestamp and duration.

PATCH
localhost:3000/api/workouts/{id}/feedback

Body: {"feedback": "..."}. Attach a note to a completed workout.

GET
localhost:3000/api/workouts/history?page=1&limit=10

Paginated. Add &workoutType=cardio to filter by type.

Dashboard

GET
localhost:3000/api/dashboard/

Totals, averages, most/least active day, and two chart-ready series (byDay, byType) — this is what the frontend chart binds to directly.

ADMIN

What the admin can do

A separate login, a separate session, and a wider blast radius — deletion and subscription changes live here. Test destructive calls against throwaway members only.

Session

POST
localhost:3000/api/admin/login

Body: email, password. Separate cookie from a member session — one admin account seeded.

Roster management

GET
localhost:3000/api/admin/members?page=1&limit=10

Paginated roster of every member. 252+ seeded members to page through.

POST
localhost:3000/api/admin/members

Body: fullName, email, subscriptionPlan, password, optional phone. Duplicate email → 409, bad phone → 400.

PUT
localhost:3000/api/admin/members/{id}

Partial update — e.g. {"fullName": "..."}. Returns the full updated record.

PATCH
localhost:3000/api/admin/members/{id}/subscription

Body: {"subscriptionPlan": "premium"}. Changing plan also widens allowed_workout_days.

DELETE
localhost:3000/api/admin/members/{id}

Throwaway member only — this cannot be undone. Expect 200.

Member insight

GET
localhost:3000/api/admin/members/{id}/workouts

Any member's paginated workout history, viewed as the admin — includes the member record inline.

GET
localhost:3000/api/admin/statistics

Gym-wide totals: member count, active subscriptions, total workouts and calories, most popular type.

Reports

GET
localhost:3000/api/reports/{memberId}

Full member report as JSON — profile, complete workout list, and rolled-up stats in one payload.

GET
localhost:3000/api/reports/{memberId}/qr

Returns a base64 PNG QR code, most likely encoding a link to that member's printable report.

GET
localhost:3000/api/reports/{memberId}/print

A complete standalone dark-mode HTML page — open it directly in a browser or hand it to a printer.

Authentication page

Registration and login for members. This is the only page a signed-out visitor can reach.

POST
localhost:3000/api/auth/registerpublic

Sign-up form: full name, email, password. On 409 show "email already registered"; on 400 surface the specific validation message.

POST
localhost:3000/api/auth/loginpublic

Login form. On success, redirect into the member area — the session cookie is set automatically by the response.

POST
localhost:3000/api/auth/refreshmember

Call silently in the background to keep a long session alive; no UI needed for this one.

POST
localhost:3000/api/auth/logoutmember

Wire to the logout button. Clear local state and route back to this page after.

Member home / profile page

The landing screen right after login — who they are and what plan they're on.

GET
localhost:3000/api/members/memember

Name, phone, plan, status, and allowed workout days — the source for a profile header or card.

GET
localhost:3000/api/members/me/subscriptionmember

Use this for a lightweight plan badge anywhere it needs to show without loading the full profile.

GET
localhost:3000/api/members/me/workout-daysmember

Feed this into a weekly calendar widget to grey out days this plan doesn't cover.

Workout tracker page

The core loop: start a session, stop it, optionally leave feedback, then browse history.

POST
localhost:3000/api/workouts/startmember

"Start workout" button, with a type picker limited to the seven valid values. Hold the returned id in state.

POST
localhost:3000/api/workouts/{id}/stopmember

"Stop workout" button. Ask for a calorie estimate, or compute one client-side and send it.

PATCH
localhost:3000/api/workouts/{id}/feedbackmember

Optional post-workout note field, shown right after a session ends.

GET
localhost:3000/api/workouts/historymember

The history list. Supports page, limit, and an optional workoutType filter tab.

Progress dashboard page

One call, one screen — every number and both chart series come back together.

GET
localhost:3000/api/dashboard/member

Bind totalWorkouts, totalCalories, averageDuration, and mostActiveDay/leastActiveDay to summary stat tiles. Bind chart.byDay to a weekly bar chart and chart.byType to a breakdown chart (pie or bar) — both arrive as parallel labels/values arrays, ready for most charting libraries with no reshaping.

Admin login page

A separate entry point from member login — don't reuse the member auth form.

POST
localhost:3000/api/admin/loginpublic

Admin-only credentials, no self-registration flow exists for this role — there's one seeded account.

Admin roster page

The member table admins live in day to day — list, add, edit, change plan, remove.

GET
localhost:3000/api/admin/membersadmin

Paginated table view. Build page controls around the response's total, page, limit.

POST
localhost:3000/api/admin/membersadmin

"Add member" form/modal. Validate phone format client-side too — the API rejects malformed numbers with 400.

PUT
localhost:3000/api/admin/members/{id}admin

Inline edit or an edit-member modal for name/phone/other fields.

PATCH
localhost:3000/api/admin/members/{id}/subscriptionadmin

A dedicated plan-change control — keep it separate from the general edit form since it also affects workout-day access.

DELETE
localhost:3000/api/admin/members/{id}admin

Gate this behind a confirmation dialog — it's a hard delete with no undo.

Admin member detail page

Drill into one member from the roster — their workout log and downloadable reports.

GET
localhost:3000/api/admin/members/{id}/workoutsadmin

This member's paginated workout log, viewed by the admin.

GET
localhost:3000/api/reports/{id}admin

Backs an on-page report summary — profile, full workout list, and stats in one JSON payload.

GET
localhost:3000/api/reports/{id}/qradmin

Render the returned base64 string directly in an <img src="data:image/png;base64,...">.

GET
localhost:3000/api/reports/{id}/printadmin

Wire to a "print report" button — open the returned HTML in a new tab and let the browser's print dialog handle it.

Admin overview page

Gym-wide numbers, separate from any one member's dashboard.

GET
localhost:3000/api/admin/statisticsadmin

One call for the whole overview screen: total members, active subscriptions, total workouts and calories gym-wide, and the most popular workout type.
