PHASE 1 · WARM-UP — AUTHENTICATION
01 — TWO LANES, NEVER CROSSED

A member and the admin never share a login.

Two independent sessions run side by side. A member never gets admin power by accident, because they're not even using the same system to log in.

MemberaccessToken + refreshToken

Authenticates through Supabase. Access token is short-lived; refresh token lasts 30 days.

AdminadminAccessToken (JWT)

Checked against one fixed email/password pair from the environment. Its own signed token, its own guarded routes.

PHASE 2 · THE WORKING SETS — DATA
02 — THREE STORES, THREE JOBS

No single database does all the work.

An identity, a workout, and a cached answer are three different shapes of data. Each one lives where it's handled best, instead of forcing all of it into one box.

Supabasemembers table + auth · Postgres
IDENTITY
MongoDB Atlasworkout sessions · Mongoose
ACTIVITY
Redis Clouddashboard, report & stats cache
SPEED
03 — WHAT A SET LOOKS LIKE

Start. Work. Stop. Measure.

A workout is a document, not a row: a start time, a type, an end time and duration once it's stopped, calories if given, and optional feedback after. Written once, read back on the dashboard.

PHASE 3 · COOLDOWN — CACHING
04 — RECOVERY TIME, ON PURPOSE

Three pages don't need a fresh answer every time.

A dashboard, a report, and the gym's overall numbers get asked for constantly but don't change every second. Redis holds the last answer so the other databases can rest.

Member dashboard10 min
Member report (+ QR, print)30 min
Gym-wide statistics5 min
PHASE 4 · FULL SET LIST — THE API
05 — EVERY MOVE, COUNTED

24 endpoints. Every one checked before it runs.

Every request's body, query, and params pass through a Zod schema before a controller ever touches them — a malformed request never gets far enough to do damage.
